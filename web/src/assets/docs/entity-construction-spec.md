> 适用：领域实体构建器维护的实体定义库（通用域）。
> 目的：让每个实体在泛化抽取、段落模板绑定和报告参数中都有确定的含义，不产生同义重复、歧义引用和无效键。
>
> 本文档由页面「构建规范」按钮直接渲染，单一来源，改这里即改页面。

## 0. 先明确三件事

| 术语         | 含义                                          | 在系统中的形态                                |
| ------------ | --------------------------------------------- | --------------------------------------------- |
| 实体对象     | 文档中可独立识别的对象（项目、河流、噪声源…） | 一条实体定义：`entity_key` + 分类 + 属性表    |
| 属性         | 某个实体的一个维度（名称、数值、状态…）       | 实体下的 `{ key, name_cn, value_type, unit }` |
| 值域（枚举） | 封闭的取值集合（保护目标类型、达标情况…）     | 属性上的 `value_type: Enum` + `enum_options`  |

实体被引用的格式是 `entity_key.prop_key`（如 `river.river_length_value`）。无点号的引用视为实体级实例。这意味着 **`entity_key` 与属性 `key` 是契约，改名或删除会让已绑定的模板和段落 slot 失效**。

## 1. 建实体，还是建属性

按顺序判断，命中即停：

1. 它是不是某个已有实体的取值或维度？→ **不建实体**，作为该实体的属性或枚举。
2. 它是不是一组封闭取值（状态、类型、类别）？→ **属性 Enum**，不建实体。
3. 它是否同时满足下面四条？→ **建实体**：
   - 在文档中能被单独识别成一个对象实例（有名称或编号）；
   - 有自己的 2 个以上属性；
   - 可能被多条关系引用，或在多个章节反复出现；
   - 不是标准编号、法规条款序号、表头、章节标题、纯数值与单位。

反例（本库曾出现的错误形态）：

- ✗ 「人居类保护目标」「文物类保护目标」等 5 个实体 —— 它们只是保护目标的一个类型取值，应作为「保护目标」实体的 `type` 枚举。
- ✗ 「工程参数」实体 —— 内容是生产能力、服务年限、井田面积、开采深度，是「工程概况」实体的属性集合。
- ✗ 「项目主体」「建设性质」「生命周期」「开采技术」 —— 都是项目本体的一两个字段。
- ✗ 「污染物」「环境要素」「判定结论」 —— 封闭取值，且已被其它实体的属性使用。

## 2. 命名规范

### 2.1 键（key）

| 对象         | 规则                                                       | 正例                       | 反例                             |
| ------------ | ---------------------------------------------------------- | -------------------------- | -------------------------------- |
| `entity_key` | 小写英文 + 下划线，`^[a-z][a-z0-9_]*$`，≤64 字符，单数名词 | `river`、`noise_equipment` | `河流`、`NoiseSource`、`river.1` |
| 属性 `key`   | 同上；同一实体内唯一（不区分大小写）                       | `river_length_value`       | `河流长度数值`、`river-length`   |

禁止：中文键、空格、点号、单位混入键名（`area_km2` ✗，单位写进 `unit` 字段）。

### 2.2 名称（name_cn）

- 用概念名词，不带括号注记：写「公用工程」，不写「公用工程（供水/电/热）」。
- 同一实体只能有一个标准名；别称放 `synonyms`。
- `synonyms` 全局不得重复：一个别名只能属于一个实体，否则检索与抽取会争抢同一词。

### 2.3 描述

- `description` 用一句话说清「这个对象是什么」，不写提取步骤、不写单位换算（那是 `extraction_hint` 的职责）。
- 属性 `description` 说明该字段的口径（例如「评价区内的面积，不含矿区外扩」）。

## 3. 类型与字段

### 3.1 实体级

| 字段           | 规则                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------- |
| `value_type`   | 带属性表的实体一律 `Object`；标量实体才用 `String` / `Integer` / `Float` / `Boolean` / `Enum` |
| `is_list_type` | 文档中会重复出现多个实例时勾选（河流、噪声源、固废…）                                         |
| `unit`         | 仅标量实体填写；带属性表的实体单位写在属性上                                                  |
| `category`     | 必须命中分类字典（见第 4 节）                                                                 |

`Object` 与 `String` 的语义不同：`String` 实体是标量实例（无属性表），`Object` 才是带属性表的容器。**不要出现「类型是 String 却维护了属性表」的定义。**

### 3.2 属性级

| 字段              | 规则                                                                                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `value_type`      | 只能是 `String` / `Integer` / `Float` / `Boolean` / `Enum` / `Object` / `List`；`Numeric`、`Number`、`Date`、`Text` 为历史别名，**禁止新写入** |
| `unit`            | 数值属性必填。物理量写实际单位（`m³/d`、`Mt/a`、`dB(A)`）；计数、年份、比例、指数等无量纲项写「无量纲」                                        |
| `enum_options`    | `Enum` 类型必填；选项用文档中出现的原词，按业务顺序排列                                                                                        |
| `required`        | 只在「几乎每份报告都会出现」时勾选（如项目名称、设计生产能力），其余保持非必填                                                                 |
| `extraction_hint` | ≤30 字，给原文线索或换算规则（「查找『涌水量』，单位统一为 m³/d」）；不重复 `description` 已说清的内容                                         |

单位不要单独建成属性。「河流长度数值 + 河流长度单位」这种拆法是错的，正确做法是数值属性 `river_length_value` 配 `unit: km`。

### 3.3 同一概念只定义一次

- 同一实体内，中英文两套键写同一个概念属于重复（`主导风向` / `wind_direction` / `dominant_wind_direction` 三写是三条无效属性）。
- 跨实体同名属性，类型必须一致（`一级保护动物数量` 不能一处 Integer、一处 Numeric）。
- 同一概念不要拆成「String 描述版 + Float 数值版」两套并存；以带 `unit` 的数值属性为准，原文描述放 `description`。

## 4. 分类归属

分类回答「这个对象在环评里管哪一段」，不按章节、不按来源划：

| 分类                                 | 回答的问题             | 典型实体                                                                 |
| ------------------------------------ | ---------------------- | ------------------------------------------------------------------------ |
| `project_basic` 基础工程实体         | 谁在建、建什么、怎么建 | 项目概况、经济技术指标、占地、公用工程、瓦斯抽采、关键地质构造、封矿计划 |
| `natural_env` 自然环境实体           | 自然环境要素是什么样   | 气候气象、地形地貌、水文地质、河流、土壤、植被、野生动物、遥感数据源     |
| `env_quality` 环境质量与污染源       | 质量如何、污染从哪来   | 大气/水/声/土壤质量现状、污染源、废水、固废、碳排放                      |
| `sensitive_target` 敏感目标与空间    | 在哪建、周围有什么     | 保护目标、居民点、生态红线、空间边界                                     |
| `measures_regulation` 措施与法规实体 | 怎么办、依据什么       | 环保治理措施、监测计划、审批历史、法规标准、总量指标、政策符合性         |
| `impact_assessment` 环境影响评价实体 | 产生什么问题、后果如何 | 沉陷影响、风险评价、综合结论、判定结论                                   |

判断口诀：**质量现状和污染源归 env_quality，自然要素归 natural_env，「工程本身」才归 project_basic。** 不要把环境质量、地形地貌、河流塞进 project_basic。

## 5. 引用与变更

- 引用格式 `entity_key.prop_key`；重命名键 = 破坏引用。改名/删除前必须先在本页的「引用」面板确认没有模板或段落 slot 使用它。
- 删除实体走回收站：软删期间 `entity_key` 仍被占用，同名实体不能重建，避免历史引用悄悄指向另一套定义。
- `relation_rules`（图谱关系推理规则）目前**没有执行方**，编辑只作存档，不会改变提取或图谱行为。

## 6. 提交前检查清单

- [ ] 名称是概念名词，无括号注记；`synonyms` 不与其它实体重名
- [ ] `entity_key` 与所有属性 `key` 均为英文 snake_case，无中文、无空格、无单位
- [ ] 同一实体内无同名属性、无中英双写、无不必要的数值/单位拆分
- [ ] 带属性表的实体 `value_type = Object`；标量实体没有属性表
- [ ] 每个数值属性都有 `unit`；每个 `Enum` 都有 `enum_options`
- [ ] `value_type` 中没有 `Numeric` / `Number` / `Date` / `Text`
- [ ] 分类按第 4 节归属，未把环境质量或自然要素放进 `project_basic`
- [ ] 与库内已有实体不重复：同名、同义、属性集大幅重合三种情况都已排查
- [ ] 若修改或删除已有键，已确认无模板/slot 引用
- [ ] `description` 一句话说清对象，`extraction_hint` 只给原文线索
