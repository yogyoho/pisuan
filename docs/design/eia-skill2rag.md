煤矿环评报告写作 Agent：技能包 + RAG 知识库设计方案

煤矿环评属于“强规范、强溯源、强责任”的文书场景，因此核心思路在于：将 RAG 作为法规与数据的唯一可信来源，技能（Skill）封装行业 SOP 与计算逻辑，Agent 仅负责结构化装配与论证组织。任何无法溯源到条款或实测数据的结论一律不予输出。以下提供一套可直接落地的设计方案。

# 一、先划边界（这一步决定成败）
|维度   |设计决策|
|--|--|
|能做什么   |条款检索与适用性判断、评价等级/范围判定、源强与“三本账”核算、沉陷与预测参数计算、措施可行性论证骨架、章节初稿生成、一致性校对、质检清单打勾|
|不能做什么   |代替编制主持人签字；代替现场踏勘与监测布点决策；编造监测数据；对生态保护红线、水源地等敏感区结论做最终判定|
|责任归属   |输出物必须带“引用链 + 置信度 + 人工复核位”，并符合《建设项目环境影响报告书（表）编制监督管理办法》：建设单位负责、技术单位担责、编制主持人须为环评工程师且全职|
|数据红线   |涉涉密地理信息、矿区坐标、水文地质资料不出内网；模型与知识库私有化部署|

# 二、总体架构（五层）
```
交互层：对话 / 章节编辑器 / 评审看板 / 一键导出(docx+附件清单)
编排层：主编排器(状态机) → 子Agent(总则/工程分析/现状/预测/措施/风险/结论) → 质检Agent → 评审模拟Agent
技能层：SKILL.md + MCP工具集（法规检索、限值查询、源强计算、等级判定、GIS叠加、质检、组装）
知识层：RAG（条款库｜事实/阈值库｜案例库｜术语库｜模板库）+ 向量库 + 结构化事实表 + GIS图层
数据层：法规原文/标准/地方政策/历史报告书/监测报告/矿区基础数据/审批批复库
```
关键原则：知识层只存“可核验的事实”，技能层只存“可复现的逻辑”，Agent 不凭记忆写专业内容。

# 三、RAG 知识库设计

## 3.1 语料分层（煤矿领域必须拆这么细）
|库   |内容   |用途|
|--|--|--|
|法规标准库   |环评法、建设项目环保管理条例、分类管理名录(2021)、公众参与办法、HJ 2.1总纲、HJ 619-2011煤炭采选、HJ 2.2/2.3/610/2.4/19/964/169、GB 20426-2006、GB 18597-2023、GB 18599-2020、HJ 672/651/652、HJ 446-2008、HJ 463-2009、清洁生产、排污许可技术规范   |条款级引用、等级判定、限值核对|
|政策与准入库   |生态环境分区管控（三线一单）、国土空间规划、矿区总体规划及规划环评审查意见、产能置换、瓦斯抽采利用、保水开采、重大变动清单、碳达峰/碳排放环评试点、新污染物（环环评〔2025〕28号）   |合规性分析章、环境可行性结论|
|地方细则库   |省厅排放标准加严项、含盐量/矿井水外排要求、沉陷区搬迁政策、地方功能区划   |避免“国标对、地方错”|
|案例库   |已批复煤矿报告书（曹家滩类大型矿井、露天矿、选煤厂、风井场地、矿区修复治理工程）的章节片段与评审意见   |few-shot 风格对齐、论证句式复用|
|事实/阈值库   |从标准里抽出的结构化断言：如“矿井水确需外排时含盐量不得超1000 mg/L”“禁止建设永久性煤矸石堆放场”“优先井下充填处置矸石”“高瓦斯/突出矿井须建瓦斯抽采与综合利用设施”   |直接用于质检规则引擎，不走向量模糊匹配|
|术语与同义词库   |矸石/煤矸石、盘区/采区、首采区、疏干、保水开采、三本账、以新带老   |解决用户提问与法条表述不一致的问题|

## 3.2 元数据 Schema（这是 RAG 好不好用的分水岭）
```yaml
doc_id: HJ619-2011
title: 环境影响评价技术导则 煤炭采选工程
type: standard          # law | standard | policy | local | case | template
org: 生态环境部
status: 现行             # 现行/修订中/已废止（被替代指向新doc_id）
effective_date: 2012-01-01
region: CN              # 省码用于地方细则
chapter: 6.2 地下水环境影响评价
clause_no: 6.2.3
page: 18
hash: sha256(...)       # 用于版本变更检测
tags: [地下水,含水层,疏干,保水开采]
applies_to: [井工开采,露天开采,选煤厂]   # 适用条件，检索时做硬过滤
```
要点：检索时必须先按 status≠已废止、region、applies_to 做硬过滤，再做向量召回。否则极易出现“引用了已废止标准”这种致命错误。

## 3.3 切分策略

- 条款级切分：以“条/款/项”为最小单元，保留层级路径（如 HJ 619-2011 > 6 > 6.2 > 6.2.3），禁止按固定字符数硬切。
- 表格结构化：排放标准限值表、评价等级判据表全部解析为结构化表（字段化），单独存入事实库。向量检索对表格极不友好，而环评恰恰大量依赖查表。
- 双路索引：条款原文走稀疏+稠密混合检索（BM25 + embedding）；数值阈值走精确 KV 查询。
- 父文档回填：召回条款后附带该条所属章节的上下文 500–1000 字，防止断章取义。

## 3.4 检索路由（Query Classifier）
```
用户/Agent请求 → 分类器 → 
  ├─ 条款/依据类 → 法规标准库（混合检索 + 硬过滤 + 父文档）
  ├─ 数值限值类 → 事实/阈值库（精确匹配，SQL式）
  ├─ 怎么写/范式类 → 案例库 + 模板库（top-k 段落作 few-shot）
  ├─ 空间类（是否压覆红线/沉陷影响村庄）→ GIS 图层叠加服务（不是向量库）
  └─ 计算类（源强、沉陷参数、三本账）→ 确定性计算工具，禁止LLM心算
```

## 3.5 强制引用与时效守卫

每次生成专业陈述时，Agent 必须输出：
```json
{"claim":"矿井水确需外排时含盐量不得超过1000 mg/L",
 "evidence":[{"doc_id":"GB20426相关管理要求","clause":"矿井水外排控制要求","confidence":0.92}]}
```
- 无证据 → 标记为“待核实”，不进入正文，只进“待办清单”。
- 引用到 status=已废止 或 effective_date > 今天 → 阻断并告警。
- 每日对知识库做哈希比对，标准更新时自动标红所有引用该标准的章节（这点对环评极其重要，标准换版意味着整本报告返工）。

# 四、技能（Skill）设计

技能包采用 SKILL.md + 工具集 + 模板 + 校验规则的形态，加载即注入工作规范。

## 4.1 SKILL.md 骨架
```markdown
# 煤矿环评报告编制技能

## 角色与约束
- 你是环评编制辅助Agent；所有专业结论必须有知识库引用；不得编造监测数据与坐标。
- 输出语言：中文；正文风格：客观、第三人称、可核查。

## 适用标准（自动从知识库取最新版本，勿硬编码）
HJ 2.1 总纲｜HJ 619-2011 煤炭采选｜HJ 2.2/2.3/610/2.4/19/964/169
GB 20426-2006｜GB 18597-2023｜GB 18599-2020｜HJ 672/651/652｜HJ 446-2008

## 编制SOP（状态机）
立项判别 → 总则（等级/范围/重点/标准）→ 工程分析 → 现状调查与评价 
→ 影响预测（施工期/运行期/闭矿期）→ 措施可行性论证 → 环境风险 
→ 碳排放/新污染物（如需）→ 公众参与 → 环境管理与监测计划 → 结论 → 附件清单

## 必检清单（部分）
[ ] 评价等级与各要素导则判据一致且有引用
[ ] 敏感目标（红线、水源地、基本农田、保护动植物）逐一核实并附图
[ ] 地表沉陷给出最大下沉值、倾斜、曲率、水平移动/变形、影响半径
[ ] 矿井水优先回用，外排含盐量≤1000mg/L且不影响下游水功能
[ ] 煤矸石优先井下充填，不设永久性矸石场；危废暂存满足GB18597-2023
[ ] 高瓦斯/突出矿井配套瓦斯抽采与综合利用
[ ] 洗煤废水闭路循环零排放；储煤封闭、全封闭廊道、布袋除尘
[ ] "三本账"平衡、排放总量与排污许可衔接
[ ] 闭矿期生态恢复与土地复垦方案、资金与管护
[ ] 编制单位和编制人员情况表（信用平台导出）
```

## 4.2 工具集（MCP，建议至少这些）
|工具|职责|输入/输出要点|
|--|--|--|
|search_regulation|条款检索|query, element, region → 条款列表+引用|
|get_limit   |限值/判据精确查询   |standard, table, key → 数值|
|determine_grade   |评价等级判定   |要素+项目参数 → 等级+判据引用|
|calc_source_strength   |源强核算（粉尘、瓦斯、矿井水、噪声）   |工艺参数 → 源强表|
|calc_subsidence   |地表沉陷参数   |煤层厚度、埋深、采厚比、岩性 → 下沉/倾斜/曲率/变形/半径|
|water_balance   |水量平衡与三本账   |用水/排水节点 → 平衡表|
|gis_overlay   |敏感区空间叠加   |井田范围/沉陷范围 + 红线等图层 → 冲突清单+面积|
|check_compliance   |条款级合规检查   |章节文本 → 不符合项列表|
|consistency_check   |跨章节数据一致性   |全文 → 冲突（如同一个矸石量两处不一致）|
|assemble_report   |按大纲组装 docx + 附件清单   |章节产物 → 成稿|
|review_simulator   |模拟技术评估中心提问题   |章节 → 质询问题清单|

重要：凡涉及数字的地方（源强、沉陷、总量、距离、频次），一律走计算工具，不允许大模型自己推算。

# 五、Agent 编排：把“写报告”变成流水线
```
Phase 0 立项判别：分类管理名录 → 报告书/报告表/登记表；是否需辐射专篇（伴生放射性矿）
Phase 1 信息收集：项目基础信息表单（必填槽位：规模、井型、工艺、井田面积、煤层、瓦斯等级、选址坐标、受纳水体…）缺槽位就追问，不许猜
Phase 2 总则：等级/范围/重点/标准/时段（建设期+运行期+闭矿期）
Phase 3 工程分析：工艺流程→产污环节→源强→三本账→清洁生产指标
Phase 4 现状：监测方案建议 + 现状评价（数据来自用户上传的监测报告，Agent只做统计与达标判定）
Phase 5 预测：分要素并行（大气/地表水/地下水/声/生态/土壤/风险），各自子Agent产出
Phase 6 措施与论证：技术可行+经济合理+长期稳定+达标可靠四维论证骨架
Phase 7 结论与附件：结论三段式（现状—影响—措施—可行性）+ 附件/图件清单
每阶段结束 → 质检Agent打勾 → 人工卡点确认 → checkpoint落盘
```
编排要点：单源数据（项目基础信息存一份 JSON，所有章节只读它，禁止各章各自改写）；每阶段产物独立落盘，支持回滚与差异对比。

# 六、质量控制与防幻觉

1. 引用门禁：正文每条专业断言后附 [HJ 619-2011 §6.2.3]，无引用不进正文。
2. 双 Agent 互审：编写 Agent 与质检 Agent 分离，质检只用条款库做比对，不看编写者的推理过程。
3. 评审模拟：用 review_simulator 扮演技术评估中心，针对“评价重点为何是生态和地下水”“矸石综合利用去向是否落实”“沉陷区搬迁安置谁出钱”等高频质疑点生成问题清单，倒逼补证。
4. 数值一致性扫描：同一指标（如矸石产生量、矿井水量、投资额）在全文出现的所有位置做交叉校验。
5. 不确定性标注：对依赖假设的结论（如后期风井场地未设计、管线单独立项）显式标注“本次不评价/另行立项”，这正是真实报告书的标准写法，也能防止越界。

# 七、落地与评测

- 技术选型：知识库用 Postgres + pgvector（条款元数据过滤友好）；表格解析单独做结构化管道；GIS 用 PostGIS；编排用 LangGraph/自研状态机；导出用 docx 模板（样式锁定，避免格式被审）。
- 评测集：拿 20–30 本已批复的真实报告书做 golden set，构造三类用例：①条款问答准确率 ②等级/限值判定正确率 ③质检项召回率（故意埋错看能否查出）。上线门槛建议 ≥95% 的引用可溯源率。
- 冷启动顺序：先做“条款检索 + 质检清单”（价值最高、风险最低），再做“总则与等级判定”，最后做“章节生成”。不要一上来就让模型写全文。
- 人机分工界面：现场踏勘记录、监测数据、敏感目标核实、公众参与原始材料，这四类必须由人上传原件，Agent 只做整理与核验。

# 八、几个容易踩的坑

- 标准版本漂移：HJ 2.1 已在修订（新增温室气体排放评价、质量控制要求、引用资料时效性等），一旦发布，总则、结论、监测计划全章要改。所以 status/effective_date/替代关系 字段必须严谨维护。
- 地方严于国标：陕西、山西、内蒙古等地对矿井水、沉陷区治理有专门规定，只挂国标会被退回。地方细则库要按省分片。
- 表格是 RAG 的盲区：排放限值、等级判据、清洁生产指标全是表，务必结构化，否则检索出来也是废的。
- 不要把案例当依据：案例库只能提供写法范式，不能作为合规依据，引用时必须区分“依据”与“参考”。
- 署名合规：AI 生成的内容不能替代环评工程师的专业判断，交付物中应保留修改痕迹与复核记录，便于归档备查（档案管理要求基础资料、踏勘影像、质控记录一并存档）。

# 九、50份样例报告的真实价值：不在“语料量”，而在“结构锚点”

50份报告远不足以训练模型，但足以完成四件别处拿不到的事：建立评测集、沉淀写作范式、标定数值合理性区间、反推质检规则。它们的核心作用是作为校准器与裁判，而非单纯的素材库。下面按价值排序拆解。

## 一、先分清：这50份里哪些是金子，哪些是沙子
|类型|价值|说明|
|--|--|--|
|已批复版 + 技术评估意见 + 修改说明（三联套）   |★★★★★   |这是唯一能告诉你“哪里会被打回、怎么改才过”的数据。一条“意见→修改后文本”的对齐样本，胜过十份正文|
|已批复版正文（无意见）   |★★★   |写法范式、章节骨架、论证句式、图件清单|
|未批复/退回重编版   |★★   |反面教材，适合做“错误注入”评测用例|
|同一矿区不同版本（报批稿 vs 公示稿）   |★★★   |看删改痕迹，能反推敏感表述与合规边界|

如果这50份全是纯正文、没有评审意见，建议优先去补10–20套“意见+修改说明”，ROI 远高于再凑30份正文。省级生态环境厅公示平台、环评信用平台的公开版本是合法来源。

## 二、能提取什么：分五层，价值递减

### 第1层｜元数据与适用性标签（最便宜，最该先做）

从封面、目录、总则章抽取：
```YAML
doc_id: MH-2023-SX-017
province: 山西
mine_type: 井工开采 / 露天 / 选煤厂 / 风井场地 / 修复治理工程
scale_Mt_a: 5.0
approval_year: 2023
approval_org: 生态环境部 / 省厅
EIA_grade: 报告书
standards_cited: [HJ2.1-2016, HJ619-2011, GB20426-2006, ...]
evaluation_elements: [生态,地下水,大气,声,土壤,风险]
key_sensitive_targets: [生态保护红线,饮用水源,基本农田,村庄搬迁]
chapter_structure: {大气: "4.3", 地下水: "5.2", ...}   # 目录树
```
用途：① 做检索时的硬过滤维度（province、mine_type）；② 自动推荐“同类项目参考段落”；③ 发现地域差异（比如陕西本子普遍多一章“保水开采专题”，内蒙古普遍有“沉陷区搬迁安置”专节）。

### 第2层｜事实槽位与数值区间（核心资产，用于校验而非生成）

从工程分析、三本账、措施章抽取结构化字段：
|字段族   |示例字段   |提取后怎么用|
|--|--|--|
|工程参数   |井田面积、可采煤层数/厚度、埋深、采煤方法、采厚比、服务年限、瓦斯等级、瓦斯抽采率   |作为 calc_subsidence 等工具的输入域合法性检查（超常识值告警）|
|源强   |粉尘产生量/排放量、矿井水量(m³/d)、COD/SS/氯化物浓度、噪声源强、矸石产生量(t/a)、瓦斯排放量   |建单位产能指标分布（如 t 粉尘/Mt 煤），新报告算出的值若偏离 P5–P95 就标黄|
|三本账   |现有工程排放量、拟建项目排放量、以新带老削减量、增减量   |直接生成“三本账核对规则”：全篇所有出现该数的位置必须一致|
|措施参数   |储煤场封闭面积、除尘器效率%、矿井水处理工艺链、回用率%、矸石充填比例、复垦面积、绿化率   |生成措施可行性论证的骨架槽位（工艺链 = 单元序列，可做成可选模板）|
|监测计划   |监测点位、因子、频次、执行标准   |直接产出监测计划表草稿——这是最模板化、最容易自动生成且风险最低的一章|
|投资与进度   |环保投资额及占比、工期   |一致性校验锚点|

关键点：这些数字不是拿来抄的，而是用来建“合理性护栏”。Agent 自己算出的源强，要和同类型矿井的分布比对；偏差过大时提示“请复核参数”，而不是悄悄替用户抹平。

### 第3层｜论证结构与句式范式（解决“写得像不像”）

对每一章做** rhetorical 标注**（不必全文标，每类章节标 3–5 份即可）：

- 结论章三段式：现状结论 → 影响结论 → 措施可行性 → 总体可行性判定
- 符合性分析：政策条款原文 → 本项目情况 → 相符/不相符判定（这个三元组可以直接抽成结构化记录，喂给 RAG 的“政策准入库”）
- 不确定性处理句式：“鉴于××尚未设计，本次评价仅针对××，××另行立项评价”
- 搬迁安置的责任主体与资金表述模式

产出物：一个 few-shot 片段库，按 (章节, mine_type, province) 索引，检索时取 top-2 作风格对齐。必须同时存“依据来源”字段，防止模型把案例写法当成法规要求。

### 第4层｜图件与附件清单（最容易被忽略，却是评审高频扣分点）

从“附图附件”页抽取标准化清单，并标注哪些是必备项（出现频率 >80% 的视为必备）：
```
必备图件：地理位置图、井田及周边关系图、地层综合柱状图、水文地质图、
          地表沉陷等值线图、生态保护措施平面布置图、监测布点图、
          土地利用现状图、环境敏感目标分布图
必备附件：采矿许可证/划定矿区范围批复、矿区总体规划环评审查意见、
          监测报告、公众参与说明、编制单位和人员情况表、危废协议
```
做成 checklist.json，质检 Agent 直接逐项核对文件是否齐全——这一条落地快、争议小、用户感知强。

### 第5层｜评审意见→质询问题库（把“被动挨问”变“主动预演”）

从技术评估意见里抽取问题，归一到固定 taxonomy：
```
[评价重点] 为何将生态和地下水列为评价重点？大气为何不做进一步预测？
[等级判定] 地下水评价等级判定依据中包气带防污性能取值依据不足
[敏感目标] 井田范围与生态保护红线重叠面积未核实，需附图
[矸石] 矸石综合利用去向协议未落实，临时堆放场选址合规性论证不足
[闭矿] 闭矿期生态恢复责任主体与资金未明确
[数据一致性] 正文P42矸石量与表3-5不一致
```
这就是 review_simulator 的问题池。50份报告的意见通常能覆盖 80–150 条高频质询，且每条都能挂到对应条款上（因为评审意见本身就是条款驱动的）。这是极佳的“条款↔典型缺陷”配对数据。

## 三、要不要提前加工？要，而且加工成本占整个项目的一半

原始 PDF 直接进向量库基本是浪费，原因有三：扫描件多、表格多、跨章引用多、版本混杂。建议流水线如下：
```
① 格式归一化
   PDF(含扫描) → OCR(PaddleOCR/商用) → 双层PDF + 文本
   ⚠️ 扫描件表格是最大难点，单独走表格识别通道

② 结构解析（最关键一步）
   用"目录树"做骨架，把正文切到 [章-节-条] 三级，并保留页码
   → 产出：document_tree.json，每个节点带 heading_path

③ 表格结构化
   限值表/判据表 → 字段化（这部分若做得好，RAG 查表能力质变）
   三本账表/源强表 → 结构化，落事实库

④ 元数据与槽位抽取
   LLM 辅助抽取 + 人工复核（50份规模，人工复核完全可行，建议全量复核关键字段）

⑤ 去标识与合规处理
   企业名称、联系人、精确坐标、监测原始数据 → 脱敏或哈希
   确认来源为公开公示版本，保留来源URL与公示日期（版权与溯源）

⑥ 切分与索引
   条款级切分 + 父文档回填 + 混合索引（BM25 + embedding）
   元数据写进 pgvector 的 metadata 列，供硬过滤

⑦ 人工标注种子集
   挑 5–8 份做深度标注（章节角色、论证结构、意见对齐），其余走弱监督
```
一定要做的两件事：
- 版本指纹：每份报告记录所引用的标准版本（如 HJ 2.1-2016）。将来标准换版时，你能一键定位“哪些样例本身已过时”，避免用旧范本教出旧写法。
- 冲突标记：50份之间必然互相矛盾（不同省份、不同年份）。不要在知识库里强行统一，而是把矛盾显式记成 variant 字段，检索时按 province + year 过滤。否则 Agent 会学到“有时可以、有时不行”的混乱认知。

## 四、明确的边界：样例不能干什么

1. 案例 ≠ 依据。样例库只能支撑“怎么写”，绝不能支撑“为什么可以”。生成时若引用了样例里的做法当作合规理由，属于严重错误，必须在 prompt 和质检里双重禁止。
2. 不要学超标值。老报告里的排放浓度、沉陷预测值是特定项目的结果，不是阈值。阈值只从标准库取。
3. 不要学省略。早期报告常省略碳排放、新污染物、闭矿期等内容，用它们当范本会把遗漏固化。建议只选用近 3 年、已批复的报告，并加一条“缺章检测”规则。

## 五、建议的投入顺序（按 ROI 排）
|阶段|什么 | 交付物 | 收益
|--|--|--|--|
|W1–2   |元数据 + 目录结构 + 图件附件清单   |元数据表、checklist.json   |立刻能做“同类推荐”和“缺项检查”|
|W3–5   |评审意见抽取与归一化   |质询问题库（挂条款）   |review_simulator 可用，用户感知最强|
|W4–7   |事实槽位与数值区间   |合理性校验规则集   |数值护栏，大幅降低幻觉危害|
|W6–9   |5–8份深度标注 + 片段库   |few-shot 库   |章节生成质量提升|
|持续   |构造 golden set   |100–200 条评测用例   |没有它你无法判断任何优化是否有效|

最后一句提醒：50份的最大风险不是太少，而是没有评测集就等于没有进步的可观测信号。建议在动手抽取之前，先从这50份里手工造出 50 道“条款问答 + 20 道等级判定 + 30 个故意埋错”的用例并定好答案。有了这把尺子，后续所有的抽取和加工才知道做对了没有。
