# 领域实体构建器页面设计诊断与改进建议

> 日期：2026-11-14　　范围：`/domain-factory/general/entity-builder`（`web/src/views/DomainEntityBuilderView.vue`）
> 方法：页面源码逐行 + 后端 router/service/repository + 三处消费方交叉核对 + 生产库只读体检（`domain_entity_schemas` 71 条实体 / 592 条属性）+ 比对逻辑只读复现
> 定位：只诊断不改码。修复项进入下一轮实现批次。

---

## 0. 结论先行

页面骨架是合格的：页头操作分层清晰、左树右编、`?entity_key=` 深链、JSON 视图、克隆都有。问题不在"长得怎么样"，而在**它承诺的三件事里有两件没有落地**：

1. **AI 提取 → 比对 → 导入这条闭环，在当前数据下必然失败**：命中任一"有属性"的实体（71 个里 53 个）就抛 `AttributeError`，整个提取请求 500；就算命中"无属性"实体，产出的「有变化」项导入时也是空操作；「新增」项则会把实例值写进 schema 字段并生成随机 `entity_key`。生产库里 `metadata.source=ai_extract` 的实体数为 **0**，说明这条闭环从未真正跑通过。
2. **「图谱关系推理规则」没有任何消费方**：全仓库只有本页面在读写它，图谱构建链路从不读——27 个实体上已沉淀的规则是**死资产**。
3. 页面的真实产出（实体属性）喂给泛化 LLM 时被 `max_items=60` 截断，而截断顺序是 `category` 字母序：**`project_basic` 的 470 条属性（占全部 592 条的 79%）从未进入过泛化 prompt**。

一句话概括设计定位的偏差：**这是一台"只写不验"的控制台**——写得进，但看不见写的东西被谁用了、用得对不对。

共 **5 个 P0 / 7 个 P1 / 8 个 P2**，改进分三档（见 §5）。

## 1. 页面在链路中的真实位置

```
                    ┌───────────── 写入口 ①（本页面 CRUD）──────────┐
                    │                                              │
范例报告 ──ETL泛化──┤  domain_entity_schemas  ←── 写入口 ②（工作台 Step2 │
   │                │  （71 实体 / 592 属性）      confirm_proposed_entities）│
   │                └───────┬──────────────┬──────────────┬────────┘
   │                        │              │              │
   │               ① 泛化 prompt   ② 工作台变量面板  ③ 槽位绑定 entity_ref
   │          _load_entity_schema_variables  _convert_db_entities_to_variables   前后端两套实现
   │                cap=60            description→prompt
   │                        │              │              │
   └────────────► 学习模板 slots.entity_ref ──► commit 入库 ──► 写作侧消费
```

- 页面自身不产出任何"内容"，它维护的是**概念契约**：写报告时 LLM 该把什么当实体、每个实体有哪些属性、属性该怎么提取。
- 因此它的质量不是"能不能编辑"，而是**契约是否被下游正确消费**——这正是当前最薄弱的一环。

## 2. 现状结构梳理

### 2.1 布局与组件

| 区块 | 内容 | 行号 |
|---|---|---|
| 页头 | 标题 + 副标题 + `导出` `导入` `AI 提取` `新建实体` | 4-26 |
| 左栏 340px | 搜索框 + 树（分类节点 → 实体节点 → `+ 新建实体`） | 40-84 |
| 右栏 | 基础元数据卡 / 属性结构定义卡 / 图谱关系推理规则卡 / 操作条 | 87-274 |
| 弹窗 ×6 | 属性、规则、导入、JSON 查看、克隆、AI 提取（2 步） | 278-591 |

### 2.2 一次编辑的完整链路

```
点树节点 → normalizeEntityForEditing(深拷贝+类型归一化) → 就地编辑
   ├ 属性/规则 → 弹窗编辑，写回内存数组（不落库）
   └ 保存 → PUT/POST 全量对象 → loadData() 重新拉 taxonomy+entities（2 请求）→ 展开态被重置
```

### 2.3 三个结构性事实

- **分类树是"假层级"**：后端 `get_taxonomy` 由 `SELECT DISTINCT category` 反推 domains，`domain_id === category`，每个 domain 恒有且只有一个 category（`domain_entity_service.py:60-96`）。页面标题里的"层级分类体系"实际是 6 个平铺分组。
- **空分类不出现在树里**：`treeData` 对 0 实体的分类直接 `return null`（view:723），`+ 新建实体` 节点只挂在非空分类下（view:737-743）。分类清空后就无法从树里再建回来。
- **页面是"全量域"的**：`getTaxonomy(null)` / `listEntitySchemas(null, null)` 不带 domain 过滤（view:850-851），但所有写操作硬编码 `domain_code='general'`（view:815/936/1166/1266/1302）。当前库里只有 general 所以无感；一旦出现第二个域，页面会显示别的域数据、写回时篡改成 general。

## 4. 缺陷清单

### P0-1　AI 提取比对必然崩溃（实测复现）

- `_compare_extracted_with_entities`（service:383-438）把提取到的**实例值**（dict）与已有实体的 **`properties`**（属性定义列表）对比：
  - `existing_values = existing.get("properties", {}) or {}` 拿到的是 **list**；
  - service:416 `existing_values.keys()` → `AttributeError: 'list' object has no attribute 'keys'`。
- 只读复现：命中"有属性"实体（53/71）→ 抛异常；命中"无属性"实体 → 返回 `different` 但 diff 为空；未命中 → `new`。
- 结论：只要模型提取出的实体命中任何一个有属性的已有实体，整个 `/extract` 请求 500（router:311 兜底成"实体提取失败"）。生产库 `metadata.source=ai_extract` 为 0，与此一致。

### P0-2　「有变化」导入是空操作（死分支）

- 前端可勾选项 = `_status !== 'matched'`（view:529），即 `new` + `different`，全部提交；
- 后端只处理 `status == "new"` 与 `status == "updated"`（service:353/371），而比对**从不产出** `updated`；
- 结果：用户勾选"有变化"→ 看到"导入完成：新增 0 个，更新 0 个"→ 什么都没发生，且无错误提示。

### P0-3　「新增」导入把实例值写进 schema，并伪造 entity_key

- service:354-367：`"properties": item.get("values", {})` —— **把 `{属性名: 实例值}` 写进本该是属性定义列表的字段**（模型声明 `default=list`）；当前库中没有 dict 形态（因为从未成功执行），一旦执行，`_convert_db_entities_to_variables`（service:511 直接 `for prop in properties`）会抛异常并整体回退到 JSON 文件，工作台变量面板静默降级。
- `entity_key = f"{schema_ref}_{domain_code}_{uuid8}"`（service:356）：实例本属于已有 schema，却新建了一个随机键的重复概念，破坏槽位绑定与图谱实体对齐。
- `metadata.extracted_at` 恒写 `""`（service:366）。

### P0-4　「图谱关系推理规则」无消费方

- 全仓库检索 `relation_rules`：只有本页面、model、repository、`confirm_proposed_entities` 的 `[]` 占位。图谱构建（`graph_builder.py`）与写作技能都不读。
- 27 个实体已沉淀规则，**编辑它们对系统行为零影响**。这是典型的"看起来在配置系统，其实在配置一个黑洞"。

### P0-5　两个写入口语义分叉

| 维度 | 本页 builder CRUD | 工作台 Step2 `confirm_proposed_entities` |
|---|---|---|
| 写方法 | `DomainEntityService.create/update` | 直调 `repo.create/update`（绕过 service 归一化） |
| 更新后 remap | ❌ 无 | ✅ `_remap_waiting_review_tasks`（factory:6554-6561） |
| 值类型词表 | String/Integer/Float/Boolean/Enum/Object/List | 工作台弹窗只有 **String/Numeric/Boolean/Date**（EtlWorkbench:2043-2047） |
| 缺省分类 | `project_basic`（view:929） | `其他`（factory:6527）——不在 6 类字典里，会在树上多出一个域 |
| 属性去重 | 无 | add_property 路径有（factory:6502） |

后果：在本页把某个属性的 `name_cn` 改掉，**不会**触发待审核任务的 `entity_ref` 重映射；工作台弹窗里选 `Numeric` 保存后，本页一打开就会被 `normalizeValueType` 归一化成 `String`（view:687-698），保存即丢信息。

### P1-1　`entity_ref` 两套格式

- 前端 `suggestEntityBindings`：`${entity_key}.${p.key || name_cn}`（EtlWorkbench:141）
- 后端 `_auto_map_slots_to_entity_properties`：list 形态取 **`name_cn`** 作为后半段（factory:6146-6148），dict 形态取 key（factory:6137-6140）
- 同一套数据、两种 ref：`air_quality_status.污染物名称` vs `air_quality_status.pollutant_name`。下游 `lightrag.py:667` 只是把 ref 拼进分块文本作检索提示，错了不报错、只降质。

### P1-2　分类体系不可管理

- domain/category 一对一（假层级），无法增删改分类，`CATEGORY_DOMAIN_MAP` 硬编码 6 类，未知分类走 `_build_default_domain_info` 随机造一个域（service:99-106）。
- 空分类不可见、不可从树新建；页头"新建实体"总是落到 `project_basic`。
- 分类既决定树分组，又决定 prompt 截断优先级，却没有 `sort_order` 或权重概念。

### P1-3　删除无影响面

- 属性/实体被 `learned_templates.slots[].entity_ref`、`domain_factory_outlines`、待审核任务段落引用；删除只做 `DELETE`，不检查、不提示、不可恢复。
- 删除后 ref 变成悬空字符串，下游静默降质（同 P1-1 的失败模式）。
- 另有软删除需求（误删 71 个实体里的一个，没有回滚手段）。

### P1-4　无脏状态守卫、无并发控制

- 切换树节点直接覆盖 `editingEntity`（view:885-891），未保存编辑静默丢失；路由离开也无提示。
- 保存是"全量覆盖数组"，无 `updated_at` 乐观锁；两个管理员同时编辑时后写者覆盖前者，且无任何提示。
- `loadData()` 每次保存后重置 `expandedKeys`（view:855-857），新建实体后也不会自动选中。

### P1-5　导入/导出不对称

- 导出含 `taxonomy` + `entity_schemas`（repo:189-259），导入只认 `entity_schemas`，`taxonomy` 被丢弃；
- `upsert_all` **只按 `entity_id` 匹配**（repo:147-187）：跨环境导入（entity_id 不同、entity_key 相同）会触发 `entity_key` 唯一约束 → 500；无 `entity_id` 的条目被 `continue` 静默跳过；
- 无预览、无 dry-run、无差异确认、无备份/撤销；
- 导入前不校验 `domain_code`：旧文件里的 `coal` 实体会进来，而 ETL 只按 `general` 读，形成"看得见但用不上"的幽灵实体。

### P1-6　AI 提取弹窗样式整体失效

- CSS 嵌套错误：`.extract-file-info`、`.extract-results-header`、`.extract-result-card`、`.extract-diff`、`.extract-card-*`、`.extract-import-bar` 全部写在 `.json-viewer { ... }` 内部（view:1462-1622），而 `.json-viewer` 只存在于 JSON 查看弹窗。
- 结果：提取卡片的状态色条、diff 红绿高亮、导入条蓝色背景、结果列表限高滚动**全部不生效**；`--purple-color` / `--warning-color` 也未在 `base.css` 定义（仅靠 fallback 值）。

### P1-7　AI 提取的能力边界与产品定位错位

- 页面里的 AI 提取做的是**实例值抽取**（"这份报告里某敏感点浓度多少"），而实体构建器的职责是**定义 schema**（"敏感点应该有哪些属性"）。
- 工作台 Step2 的 `discover_entities_task` 做的才是 schema 发现（新实体/新属性），两者目标重叠但算法、写入路径、UI 全部不同。
- 上传只支持 txt/md/json、UTF-8/GBK（router:286-294），与工厂主料是 docx 不匹配；`content[:12000]` 静默截断（service:498）；prompt 塞进全部 71 个 schema × 每条 10 属性（service:469），token 成本不可控且无提示。

### P2（体验与旧账）

1. 树分类节点计数重复：`title` 里已含 `(n)`（view:725），模板又渲染一次 `(n)`（view:65-67）→ `基础工程实体 (34) (34)`。
2. 搜索只匹配 `title`（分类名/实体名）（view:754），搜不到 `entity_key`、同义词、描述；无命中高亮。
3. 属性表不展示 `extraction_hint` / 描述 / 单位以外信息；不提示"该属性是否会进泛化 prompt"。
4. 属性只能一条条弹窗编辑，无内联编辑、无拖拽排序、无重复 key 校验（当前库无重复，但无防线）。
5. `batchDeleteEntities` API 已定义但前端从未调用（api:43）→ 死接口。
6. `seed_default_entities`（service:217-277）无调用方；`entity_type_router.py`（211 行，**内存 STUB**，重启丢数据）仍注册在 `/api/entity-types`，`web/src/apis/entity_type_api.js` 无任何使用者 → 同一概念存在**三套**实体接口。
7. 页头副标题、`snake_case`、`entity_key`、JSON 原文都是开发者词汇，面向领域管理员时应改写为"实体标识/中文名"。
8. 右栏空态只有一句话（view:88-90），没有"新建 / AI 提取 / 从报告学习"入口；保存/取消在长表单底部，属性多时需滚动才能点到。
9. `views/DomainEntityBuilderView.vue` 单文件 1623 行、6 个弹窗、15 个 handler 状态，无组件拆分。
10. 测试仅有路由可达/鉴权 5 条（`test_domain_entity_builder_api.py`），前端 0 条；`_compare_extracted_with_entities`、`save_extracted_entities`、import/export 往返、remap 全部无覆盖。

## 5. 改进建议

### 5.1 第一档：保真修复（先让已有功能真的能用，1–2 天）

| # | 动作 | 位置 | 验收 |
|---|---|---|---|
| 1 | 重写 `_compare_extracted_with_entities`：不再拿实例值与属性定义对比。语义改为"覆盖度比对"——提取结果的**属性键集合** vs 已有 schema 的属性键集合，输出 `new / partial / matched` 三态，对应"补属性 / 建实体 / 已一致" | service:383-438 | 单测矩阵：有属性实体、无属性实体、未命中、dict/list 属性四种输入均不抛异常 |
| 2 | `save_extracted_entities` 重写：`new` 分支写 `properties=[]` 或由提取键生成属性定义；`entity_key` 复用 `schema_ref`（不新建实体）；新增 `partial` 分支实现 `add_property`；删除不可达的 `updated` 分支 | service:339-381 | 导入后打开该实体，属性表可正常渲染；`entity_key` 无随机后缀 |
| 3 | 把 `.extract-*` 样式从 `.json-viewer` 中提出来；`--purple-color/--warning-color` 换成 `base.css` 已有 token | view:1462-1622 | AI 提取弹窗出现状态色条、diff 红绿、蓝底导入条 |
| 4 | 统一写入口：`DomainEntityService.update_entity` 末尾调用 `_remap_waiting_review_tasks(GENERAL_DOMAIN_CODE)`；值类型词表统一为 builder 的 7 种，服务端拒绝未知值（不再静默转 String） | service:147-160；EtlWorkbench:2043-2047 | 改属性名→待审核任务 ref 同步刷新；工作台保存 Numeric 被拒或映射为 Float |
| 5 | 关系规则二选一：**短期**在卡片加"当前无执行方，仅存档"提示并移出主流程；**中期**接 `graph_builder` 消费或删列 | view:217-247 | 管理员不再误以为规则生效 |
| 6 | 修重复计数、`entity_key`/属性 key 正则校验（前后端）、属性 key 重复拒绝 | view:725/65；service:125-160 | 树上只显示一次计数；非法键 400 并给示例 |
| 7 | 修页面作用域：所有读接口显式传 `GENERAL_DOMAIN_CODE` | view:850-851 | 第二个域出现时页面不受影响 |

### 5.2 第二档：页面重构（3–5 天）

**拆分组件（1623 行 → 6 个文件 + 1 个 composable）**

```
views/DomainEntityBuilderView.vue        编排 + 状态（≤200 行）
components/domain-factory/entity/
  EntityTree.vue            树 + 搜索 + 新建入口（分类空态也显示）
  EntityEditor.vue          基础元数据 + 操作条（sticky）
  PropertyTable.vue         内联编辑 + 拖拽排序 + 重复校验 + "是否进 prompt"标识
  RelationRuleEditor.vue    结构化条件/动作编辑（或下线）
  EntityExtractWizard.vue   提取向导
  EntityJsonModal.vue
composables/useEntitySchemas.js           加载/保存/脏状态/乐观锁
```

**交互重设计**

- 选中实体进入"查看态"，点编辑才进入"编辑态"，或保留直接编辑但必须有脏状态守卫（切树 `confirm`、`onBeforeRouteLeave`）。

- 保存后保持当前实体选中、保持展开态；新建实体后自动定位并选中。
- 右栏空态给三个入口：新建实体 / AI 提取 / 从报告学习 schema。
- 删除前弹影响面（引用该实体/属性的模板数、待审核任务数），提示需强确认。
- 搜索覆盖 name_cn / entity_key / synonyms / description，命中高亮。

### 5.3 第三档：设计升级（1–2 周，建议与 ETL 一起做）

1. **分类建字典表**：`domain_entity_categories(code, name_cn, sort_order, color, is_active)`，实体引用 `category_code`；树由字典渲染（空分类可见可建、可排序）。泛化 prompt 截断改为**按 sort_order + 使用率**选前 N，而不是字母序；并在页面标注每条属性的"进 prompt 优先级"。

## 8. 实体提取的规则化（2026-11-14 追加）

### 8.0 结论

**需要规则。但真问题不是"没有规则"，而是已有的规则没有约束力。**

三条提取链路各自有一套规则，强度相差一个数量级；而最弱的那条（本页的 AI 提取）恰是唯一由人手工触发、最容易被当成"AI 在提取"的入口。§4 的 P0-1 / P0-3 与 P1-7 就是这条结论的实测证据，本节说明规则该长什么样。

判断标准一句话：**一条规则如果不能拒绝结果，它就不是规则，只是建议。**

### 8.1 为什么实体提取比段落抽取更需要规则

段落 slot 抽错，坏一段文字；实体 `entity_key` 抽错，是**一次 schema 变更**——同一个键同时被四个消费方使用：

| 消费方 | 位置 |
|---|---|
| 泛化 prompt 变量名 `entity_key.prop_key` | `domain_factory_service.py:4050-4091` |
| 段落 slot 自动绑定键 | `_match_slot_to_property:6173` |
| 模板元数据 `entity_ref` 契约 | 前端 `${entity_key}.${p.key \|\| p.name_cn}` |
| 图谱关系推理规则 | `relation_rules` |

因此正确原则是 **生成开放、落库闭合**：AI 可以自由提议，但写进实体库必须过结构校验和人工闸门。工作台发现链路（`discover_entities_task:6199`）已经是这个范式——`new_entity`/`add_property` 落进 `template_metadata.entity_proposals` 等待确认；缺的只是把 `bind_slot` 也纳入置信门槛，并给提议附上证据。

### 8.2 三条链路现有的规则强度

| 链路 | prompt 规则 | 结构校验 | 事后绑定 | 人工闸门 |
|---|---|---|---|---|
| ETL 泛化（`_build_text_generalize_prompt:3517` + `_PROMPT_DEFAULTS["template"]:300`） | 9 条显式规则（≤5 slot/段、单位合并、禁止无意义编号、scope/region 可选…） | ✅ `with_structured_output(GeneralizedTemplate)`（`:3642`） | 三级匹配自动绑定 | 提交时人工审阅 |
| 工作台实体发现（`discover_entities_task:6199`） | 3 类建议 + 优先级 + snake_case + "每个 slot 必须出现一次" | ⚠️ 仅"频次 ≥3"硬门槛 | `bind_slot` **自动应用** | 仅改 schema 的进候选 |
| 构建器 AI 提取（`_build_extraction_prompt:440`） | 6 条自然语言规则 | ❌ 无，贪婪正则（`_parse_extraction_response:524`） | 三级匹配 + ≥2 汉字交集 | ❌ 勾选即落库 |

三层里只有 ETL 那条用了结构化输出，而它恰好不写入实体库；两条真正写实体库的链路，校验都依赖"相信模型"。

### 8.3 已实现的六处"随意提取"

1. **`schema_ref` 没有白名单**。prompt 只说"对应的 entity_key"（`:504`），`_compare_extracted_with_entities:383` 匹配不上即标 `new`，`save_extracted_entities:339` 直接建实体——AI 编一个名字就建了一条新实体。
2. **新实体 key 是随机的**：`f"{schema_ref}_{domain_code}_{uuid4().hex[:8]}"`（`:356`）。不可读、不可复用；且因 key 随机，`entity_key` 唯一约束拦不住重复导入——同一份文档提两次就是两个实体。
3. **实例值被写进 schema 属性列**：`"properties": item.get("values", {})`（`:364`，`:376` 同）。`properties` 应为 `[{key, name_cn, value_type}]`，实际被写成 `{"排放量": "1200t/a"}`，属于用脏数据污染 schema，并非"提取不准"。
4. **`values` 的键不校验**。prompt 写的是 `"属性key": 值`（`:510`），但没有检查键 ⊆ 该实体的属性 key，乱键原样入库。
5. **`confidence` 只是装饰**。全链路唯一用途是前端按 0.8/0.5 上色（`DomainEntityBuilderView.vue:541`）；后端只原样塞进 `metadata`（`:366`）——无阈值、无默认不勾选、无"低置信不落库"。
6. **`extraction_hint` 被自己的提取器无视**。页面专门设计了"提取提示"字段（库内已填 92/592），ETL 泛化在用它，但 `_build_extraction_prompt` 的属性行只读 `description`（`:469-474`），实体级也只读 `description`（`:458-459`）——**规则字段填了，没接到提取器上**。

另有两处静默自由度：`content[:12000]`（`:498`）让 AI 实际只看了开头几千字，界面不提示覆盖范围；`properties[:10]`（`:469`）让每个实体第 11 个以后的属性永远不会被提取。

还有一层反讽：这条链路目前最常触发的是 **500**（P0-1）。也就是说"随意提取"暂时被"提取即崩"掩盖着——P0-1 一修，上面六条会立刻全部暴露。

### 8.4 规则应分五层

| 层 | 内容 | 落点 | 失败行为 |
|---|---|---|---|
| **L1 结构** | `schema_ref` ∈ 实体库白名单；`values` 键 ⊆ 属性 key（未知名单列 `_unknown` 给人看，不进 schema）；`value_type` 可解析；`is_list_type` 与值形态一致；`category` ∈ 6 类 | service，与 prompt 无关 | 丢弃 + 计数，**不得**降级成 `new` |
| **L2 口径** | 每个实体一份判据：一句话定义 + 同义词 + **反例**（如"标准编号、法规条款、数值单位不是实体"）+ `extraction_hint` + 必填属性 / 单位 / 枚举 / 范围 | 实体构建器（页面第一职责） | 缺定义或缺示例的实体在提取前告警 |
| **L3 证据** | `extracted_text` 必须是原文子串（空白归一化后 `in`）；`values` 的值应能在该片段定位 | service | 无证据 → 降级或丢弃 |
| **L4 闸门** | `confidence < 阈值` 默认不勾选；**新建实体一律进候选，不直接落库**；三级匹配仅 exact/contains + 高置信自动，`≥2 汉字交集` 一律转人工 | service + 前端 | 进人工队列 |
| **L5 度量** | 拒绝率 / 人工修改率 / 重复率 / schema 覆盖率 / 提取覆盖文本比例 | 结果页与统计 | 用于回归与调参 |

L2 是重点，也是当前页面的定位错误：**实体构建器应当是"规则的编辑器"，现在退化成了"JSON schema 表单"**。它应显式回答三件事：这条规则被哪条链路消费、命中效果如何、约束是硬还是软。`extraction_hint` 填了没人用就是这种脱节的直接证据。

反之规则也不能死到没有出口：保留"发现新实体"的通道（工作台 `new_entity` 提议 + 人工确认），把 AI 的自由度限制在提案阶段。

### 8.5 最小落地顺序

**P0（不修就等于没有规则）**

1. 修 P0-1 崩溃（`_compare_extracted_with_entities:416`）
2. L1：`schema_ref` 白名单 + `values` 键校验
3. new 分支不再直接建实体，改为候选；同时修 P0-3 的 `properties` 污染
4. 打通 `status == "updated"` 分支（比对只产 `new/matched/different`，且从不写 `_entity_id`，该分支永远不触发）

**P1**

5. `extraction_hint` 接进 `_build_extraction_prompt`，并补反例字段
6. confidence 阈值 + 默认不勾选
7. `extracted_text` grounding 校验
8. 把 `content[:12000]` 变成显式可见的"提取范围"（全文 / 选定章节 / 抽样 + 覆盖率）

**P2**

9. 规则版本化 + 用 4 个 E2E 探针的合成 docx 做规则回归语料（每条硬规则一个用例）
