# 实体软删 / 回收站 + 并发保存乐观锁（P1-3 / P1-4 收尾）

**日期**：2026-11-15
**诊断依据**：`docs/vibe/2026-11-14-领域实体构建器页面设计诊断.md`（P1-3 误删无退路、P1-4 并发保存静默覆盖）
**前置批次**：P1-2 分类字典表（已完成）

## 现状与问题

1. 实体删除是硬删除：`DELETE FROM domain_entity_schemas`。一次误点确认就永久丢失整套实体定义
   （含全部属性、关系规则、泛化描述），只剩导出的旧 JSON 文件能救——而导出是手动动作，
   大多数时候没有近期备份。页面上的删除确认只提示"不可恢复"，没有可恢复的退路。
2. 属性删除同理：`PropertyTable` 直接 `splice` 掉草稿里的属性行，一旦点了保存，该属性定义
   就从库中消失；被它支撑的段落模板 / 报告参数引用变成悬空字符串。
3. 保存没有并发控制：两位管理员同时打开同一实体，后保存的一方整份覆盖前者，双方都收到
   "实体更新成功"，谁被覆盖无人知道。`updated_at` 列一直存在，但只做展示。

## 目标

- 删除实体 = 移入回收站（`deleted_at`），回收站可列出、可恢复、可彻底删除；误删有退路。
- 属性误删在保存前可一键撤销（草稿层），保存后仍可通过实体级回收站找回实体定义。
- 保存带 `expected_updated_at` 乐观锁：版本不一致返回 409，前端弹"覆盖保存 / 重新加载"，
  由人决定，而不是静默覆盖。

## 范围

做：

1. DB：`domain_entity_schemas` 增 `deleted_at TIMESTAMP NULL`；迁移 v24（`BUSINESS_SCHEMA_VERSION` 23→24，
   `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，幂等）；`migrate_domain_factory.sql` 同步。
2. Repository：所有读取默认过滤 `deleted_at IS NULL`；新增 `soft_delete` / `restore` / `purge` /
   `list_deleted` / `count_deleted`；`update` 支持 `expected_updated_at` 原子比对
   （`SELECT ... FOR UPDATE`），冲突抛 `EntityVersionConflict`。
3. Service：`delete_entity` 改软删；`restore_entity` / `purge_entity` / `list_trash`；
   `create_entity` / `clone_entity` / AI 提案导入遇回收站键给出明确拒绝（回收站键仍占位，
   不允许静默重建同名实体）；`import_all` 逐条拒绝回收站键。
4. API：`GET /entities/trash`（声明在 `/entities/{identifier}` 之前）、
   `POST /entities/{identifier}/restore`、`DELETE /entities/{identifier}/purge`；
   列表响应加 `trash_total`；`PUT` 冲突返回 409 `{code, message}`。
5. 前端：API 封装；页头「回收站」按钮（带数量）+ 抽屉（恢复 / 彻底删除，彻底删除二次确认）；
   删除确认文案改为"移入回收站，可恢复"；保存冲突弹窗（覆盖保存走 `force`）；
   属性删除后的草稿撤销条。
6. 测试：单测（软删/恢复/彻底删除/删除态过滤/冲突/force/回收站键冲突）、
   集成 API 用例、真实浏览器 E2E（删除→回收站→恢复、彻底删除、409 冲突弹窗）。
7. 文档：本任务书、`changelog.md`、诊断文档状态注记、`.wolf` 台账。

不做（有意取舍）：

- **属性级 tombstone**：属性是实体行内 JSON 数组，没有独立行；给每个属性建墓碑会引入
  "已删属性仍随导出/导入流转"的隐性数据。属性误删的退路定为「保存前撤销条 + 实体级回收站」，
  不在 JSON 里保留幽灵属性。
- 回收站自动清理（保留期 / 定时任务）：实体表是人工维护的定义表（数百行），没有必要引入
  删除时间窗和清理任务；彻底删除是显式的第二个动作。
- 并发冲突的字段级合并：只提供"覆盖 / 重载"二选一，不做三方 merge。
- 分类字典的软删与并发锁（与本批次同构，但分类是低频字典操作，另行评估）。
- 回收站行从导出中排除（导出只导活跃实体，避免把已删除定义带进其他环境）。

## 验收标准

1. 删除实体后该实体从树与列表中消失，回收站出现该实体（含删除时间），恢复后回到原分类且
   `updated_at` 刷新；彻底删除后回收站不再有该行，且只在回收站状态下可执行。
2. 用回收站里的 `entity_key` 新建 / 克隆 / AI 提案导入，返回明确错误提示"在回收站中"，
   而不是主键冲突 500 或静默重建。
3. 两个会话基于同一 `updated_at` 先后保存：后者收到 409，弹窗可"覆盖保存"（成功）或
   "重新加载"（丢弃本次编辑）；不带 `expected_updated_at` 的调用保持旧行为（脚本兼容）。
4. 回收站里的实体不参与 taxonomy 计数、泛化 prompt 变量、导出与引用扫描。
5. 属性删除后出现撤销条，点撤销原位恢复；切换实体或保存后撤销条消失。
6. `pytest`、`ruff`、`eslint`、`prettier --check`、`vite build` 全绿，浏览器零控制台报错。
