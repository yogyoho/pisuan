# 通用域知识工厂：逐页诊断与重构清单（2026-11-14）

> 上游文档：[2026-11-13-通用域知识工厂全景梳理.md](./2026-11-13-通用域知识工厂全景梳理.md)（数据加工×消费全景、页间矩阵、§8 写报告场景价值评估）
> 本轮范围：**全量诊断，先不改码**。7 个页面 + 后端服务层一次性盘清，产出「问题 + 证据 + 优先级 + 重构边界」。
> 验证方式：静态代码审计（7 份只读诊断）+ **服务层真实栈 E2E**（真实 PostgreSQL / Neo4j / Milvus / 真实 LLM），探针数据零残留。

---

## 0. 结论先行

1. **页面最大的问题不是"功能少"，而是"链路断在中间"**：多处设计意图正确、后端能力齐备，但前端与后端之间缺一条约束或一次刷新，导致「看起来能点，实际不生效」。E2E 已证实 2 处（`entity_ref` remap 断链、旧快照覆盖），静态审计另有 4 处同类断链（提示词 3/4 页签无消费方、内容契约恒为 0、上传后轮询不自启、大纲 seed 域错位）。
2. **写链普遍缺并发与脏状态控制**：全量替换 + 无版本号 + 无离开保护，是本模块最系统性的数据完整性风险，且分散在 4 条写路径（工作台保存、入库前预存、实体确认、大纲/提示词保存）。
3. **可测试性是最弱的一环**：前端 6 个页面文件合计 6.9k 行（其中 `EtlWorkbench.vue` 3329 行）**零单测**；现有两条 E2E 已失效且会静默通过；后端 repo 层无真实 DB 集成测试。任何重构若不带测试网，都会重演同类缺陷。
4. **模块价值排序与重构投入不匹配**：工作台（★★★★★ 不可替代）恰恰是体量最大、缺陷最集中的文件；提示词页（★★☆☆☆）有一半页签是"可编辑但永不生效"的死配置，应优先下线而不是重构。

## 2. E2E 实证记录

### 2.1 实体双链路（11/11）

已在上一份文档 §7.5 记录，本轮结论不变：实体属性会进入泛化 prompt 并被 LLM 消费；LLM 提议经人工确认后落 `domain_entity_schemas`（`metadata.source=etl_proposal`）并级联 B 类区域事实草稿。两条行为观察（规则绑定吸附面大、schema 变量 cap=60 截断）保持。

### 2.2 数据源 → 工作台读链（11/11 通过）

状态机真实流转：`UPLOADED → PARSING → GENERALIZING → WAITING_REVIEW`（worker 侧无 `EXTRACTING`，与前端词表不一致，见 X1）。
读产物：段落 10 / 结构化块 6 / 泛化段落 2 / 原文 524 字符；`validate_task` 不改任务状态（但会改写 `validation_report` 列，见 §4.8.3）。

两条实测口径（写进脚本注释，避免下轮重复踩）：
- `GENERALIZING` 可能被 3s 轮询整段跳过（同脚本多轮实测有时 4 态、有时 3 态），只作观察不作断言。
- **slot 产出受 LLM 方差影响**：同一份探针 docx 多轮实测 slot 合计 = 4 / 5 / 9 / 0。当前 `system_options.default_model` 为 `openai2:agnes-3.0-flash`，最近两轮均为 0 slot——这不是脚本问题，而是"泛化 prompt 对'含数值段落应产出 slot'没有兜底校验"的直接后果（见 §4.3-P1 与 X2）。

### 2.3 工作台写语义与 remap（7/7，其中 2 条是缺陷复现）

| 断言 | 结果 | 说明 |
|---|---|---|
| S1 详情快照可取，`entity_ref` 初始为空 | PASS | 前端内存 = 服务端快照（无草稿副本） |
| S2a `SlotEntityMapper` 对 legacy 类型名可绑定 | PASS | `project_main` 精确命中 → **机制是活的** |
| S2 确认通用域实体落库 | PASS | `saved=1` |
| **S3 remap 不认实体构建页的实体** | **PASS（缺陷）** | `remapped=0`，`entity_ref` 仍为空 |
| S4a 服务端存在已绑定 `entity_ref` | PASS | 模拟 remap 生效后的状态 |
| **S4b 旧快照保存覆盖回空** | **PASS（缺陷）** | `e2e_probe_remap_entity.probe_metric` → `''` |
| S5 `structured_blocks` 全量替换 | PASS | 空数组即清空，无字段级合并/版本校验 |

**结论 A（断链，已证实）**：`confirm_proposed_entities` 触发的 `_remap_waiting_review_tasks`（`domain_factory_service.py:6554-6613`）其匹配源是**静态文件** `server/coal_eia_entity_types.json`（17 个旧实体类型，`EntityMetaLoader`，`entity_meta_service.py:19-51`），与「实体构建」页维护的 `domain_entity_schemas` 不是同一份数据。因此确认一个通用域实体**永远不会**回填工作台 slot 的 `entity_ref`。

**结论 B（潜在数据丢失，已证实）**：即使 remap 对齐了实体库，工作台"确认 → 不刷新 → 再保存"依然会把服务端绑定覆盖回空（`EtlWorkbench.vue:944-992` 确认后不 `fetchTaskDetail`，`:705-711` 保存全量提交）。修 A 之后 B 会立即变成真实故障，**两者必须同批修**。

### 2.4 入库链（commit → 5 类产物 → 消费端）

一次真实 commit（探针 KB = milvus + `ollama:bge-m3:latest`，任务由 ETL 产出，`commit_task` → ARQ worker）的实测结果：

| 断言 | 实测值 |
|---|---|
| 状态机 | `WAITING_REVIEW → INGESTING → COMMITTED`（终态 COMMITTED） |
| 产物① KB 文件 | `df_<hashstr(task_id\|kb_id,12)>`，`get_file_info` 可读 |
| 产物① 分块 | 2 个 chunk，内容含原文与"泛化模板"段落 → `_build_ingest_markdown` 的组装确实进了向量库 |
| 产物② learned_templates | 2 条，按 attribution 落库，`extra_meta.contributing_task_ids` 含探针任务 |
| 产物③ outlines | 4 条（总则/环境现状调查/环境空气质量/环境保护措施），`source_task_ids` 含探针任务 |
| 产物④ KB 归属绑定 | 1 行，attribution 与任务一致 |
| 产物⑤ 图谱 | `Document{id: doc_<task_id>}` 存在；新增 22 个节点（段落模板/章节/插槽/表格等） |
| 零残留 | 行数指纹回到"前置 − 探针任务"（5/211/632/0/0），新增图谱节点 22 个全删，总节点数回到基线 9102，共享 `ChapterTemplate` 属性 0 处漂移 |

消费端（`@tool` 装饰的 `get_templates` / `lookup_regional_fact`，经 `.ainvoke` + 真实 `ToolRuntime` 调用）：
- `get_templates` 在探针库归属下读到 1 条模板，`_source=graph`（走图谱而非 DB 回退）；
- `lookup_regional_fact` 对无事实的 region 返回 `total=0` + 结构化 hint，**不跨库/跨区混供**。

> 结论：入库链本身是通的，5 类产物都真实落库且可被写手工具消费。前面 §2.3 的两条缺陷是这条链**上游**（工作台保存/确认实体）的问题，不是入库管线的问题。

### 2.5 附带发现：`assert_kb_attribution_compatible` 名不副实

`commit_task` 的"早失败检查"（`domain_factory_service.py:4320`）走 `_assert_kb_attribution_compatible_in_session`（`domain_factory_repository.py:596-645`），而该方法在 `binding is None` 时会 **`session.add(...)` 写入绑定行**（`:636-645`）。E2E 实测：仅调用 `commit_task` 一次、流水线未跑，`domain_factory_kb_attributions` 已新增 1 行。也就是说"校验"带写副作用，且写在**入库成功之前**——入库失败会留下一条指向空库的归属绑定。

### 2.6 真实栈 E2E 的副作用地图（可复用方法论）

本模块的写入面远大于"一个任务 + 一个库"，做过一次真实 commit 才能确认下面这些点，后续任何 E2E/回归脚本都必须照此快照：

| 副作用 | 归属隔离是否覆盖 | 处理方式 |
|---|---|---|
| `domain_factory_tasks` / `learned_templates` / `outlines` / `kb_attributions` | ✅ 按 `attribution` 唯一 | 按 attribution 删除 + 行数指纹 |
| 任务中心 `tasks` 表（ETL 一行 + ingest 一行） | ❌ 无 FK | 删 `domain_factory_tasks` **不会**带走，须按 `payload->>'domain_factory_task_id'` 另删 |
| Neo4j `Document/Section/ParagraphTemplate/…` | ✅ 节点带 `attribution` 属性 | 提交前快照全部 `n.id`，结束后删除差集 |
| Neo4j 共享 `ChapterTemplate`（`CH_*_std_*`） | ❌ 无 attribution | `_merge_cross_report_knowledge` 会 SET `key_points`/`content_contract` → 快照节点全属性并回滚（本次实测回滚 12 个节点） |
| Neo4j 共享 `LegalReference` | ❌ 全局 id，`frequency +1`、可能标 `superseded` | 文档含法规引用时必须快照 `frequency/status/superseded_by` 回写 |
| Neo4j 共享 `EntitySchema` | ❌ 全局 id，`ON MATCH` 会 COALESCE 补空属性 | 同上 |
| 学习模板 `match_count` 自增 | ❌ 不按 attribution 过滤（ETL 取 top200 全表） | 上传前快照 `(id, match_count)`，结束后只回写漂移行 |
| KB（Milvus collection / MinIO 前缀 / `knowledge_files` / `knowledge_chunks`） | ✅ 按 `kb_id` | `delete_database` 会清理；**必须先走 API 再删其它行**，否则 `KBNotFoundError` 让清理整体跳过 |

两条验收纪律：
1. **不要用图谱查询 API 判"零残留"**——`_chapter_scope_filter` 恒带 `std_` 前缀，API 永远会返回种子章节（`graph_query_service.py:25-43`）。必须直连 Cypher/SQL 按 attribution 计数。
2. **ETL 与 commit 都会给自己以外的数据留痕**（`match_count`、任务中心行），指纹只数 5 张 domain_factory 表会漏。

### 2.7 附带发现②：Milvus 错误处理把真实错误替换成自己的 AttributeError

`backend/package/pisuan/knowledge/implementations/milvus.py:393`
```python
except (connections.MilvusException, RuntimeError) as e:
```
现行 pymilvus 版本里 `connections` 模块没有 `MilvusException`（它在 `pymilvus.exceptions`）。于是评估 except 元组时自身抛 `AttributeError: 'Connections' object has no attribute 'MilvusException'`，原始 Milvus 错误（实证为 `collection not found[collection=...]`）被完全掩盖，`except Exception` 分支也不会执行。

E2E 实证：worker 日志尾部是 `AttributeError`，业务侧只看到 `Failed to get Milvus collection for kb_...`。这一条不属于通用域模块，但通用域入库必经此路径，建议同批修（改用 `pymilvus.exceptions.MilvusException`）。

另有一条入库时序约束（非缺陷但会误导测试）：KB 在 worker 跑完之前被删除，会让入库以 `COMMIT_FAILED` 结束。任何自动化脚本必须等任务终态再删探针库。

## 3. 跨页系统性缺陷（横向问题）

这 11 条不属于任何单页，但决定了模块的整体质量，应作为重构的第一批批次性问题处理。

### X1 三份任务状态词表 + `INGESTING` 缺失

| 位置 | 词表 | `INGESTING` |
|---|---|---|
| `web/src/utils/taskStatus.js:2-19` | 权威映射 | 有 |
| `web/src/stores/tasker.js:37-48` | 任务中心 | 有 |
| `DataSourceDashboard.vue:34-38` | 活跃态判断 | **无** |

后果：数据源页在入库阶段停止轮询，用户看到"卡住"的旧状态。另 `EXTRACTING` 已在后端废弃（`domain_factory_service.py:853-855`），前端仍保留。

### X2 提示词三份事实源，且 3/4 无消费方

- 三份默认：`_PROMPT_DEFAULTS`（`domain_factory_service.py:285-400`）、`prompt_templates.yaml`、`PromptConfigView.vue:19-121` 前端内联，**已实质分叉**（前端是旧的通用版，运行时是环评专用版）。
- 消费端只有 `templates.get("template")`（`domain_factory_service.py:3385`）。`extract` / `schema_generation` / `section_generalization` 全仓无消费点。
- 保存总是提交 4 个键（`PromptConfigView.vue:155`），**管理员只改"文档解析"也会把前端旧版 `template` 写进 DB，覆盖 yaml 默认** → 泛化提示词静默降级。
- 变量 chip 与实际占位符不匹配：UI 给 `{extracted_data}/{slots}`，运行时只替换 `content/schema_text/chapter_hint/domain_label`（`:3528-3533`）；真正可用的键在 UI 不可见。

### X3 `entity_ref` 三种格式并存

| 产生方 | 格式 | 位置 |
|---|---|---|
| 工作台新建 slot | `entity_key.prop_key` | `EtlWorkbench.vue:141` |
| 规则绑定 | 同 `entity_key.prop_key` | `domain_factory_service.py:6173-6197` |
| `SlotEntityMapper`（remap） | 静态文件里的 `entity_id`（如 `project_main`） | `entity_meta_service.py:252-257` |

消费端（图谱 `CONSTRAINS`、`get_templates`、写手）没有统一解析入口，跨页传递会静默失配。

### X4 归属词表双源、无校验

前端 `REGION_KEY_OPTIONS` 17 slug（`AttributionEditModal.vue:14-33`，注释自认"人工同步"）vs 后端 `REGION_VOCAB`（`domain_factory_region.py:19-37`）。后端**不校验**传入 `region_key` 是否在词表内（`domain_factory_service.py:6648-6654`），前端残留旧 slug 会被持久化。

### X5 "未归属"两种语义混用

- 任务列表 `scope=unassigned` 语义是 `scope IS NULL`（`domain_factory_repository.py:1374-1377`）；
- 看板"未归属伪节点"语义是 `region_key IS NULL`（`domain_factory_service.py:7046-7047`）；
- UI 把两者都叫"未归属"（`AttributionTaskTable.vue:27,146`）。

### X6 写路径普遍无并发/脏状态控制

| 页面 | 全量替换 | 版本号 | 脏标记 | 离开拦截 | 失败回滚 |
|---|---|---|---|---|---|
| 工作台保存 | 是（`:4270-4277`） | 无 | 无 | 无 | 无 |
| 实体构建 | 整份实体 PUT | 无 | 无（切树即丢） | 无 | 仅"取消" |
| 大纲模板 | 8 字段 PUT | 无 | 无（`loadList` 先清空） | 无 | 无 |
| 提示词 | 4 键 PUT | 无 | 无（刷新静默丢弃） | 无 | 无 |

以及 4 处前端请求竞态（数据源轮询、工作台详情、大纲切章、Markdown 弹窗），**无一处有 AbortController 或请求序号**（`stores/tasker.js:115-129` 是唯一做了 requestId 防护的地方）。

### X7 demo fallback 伪造成功

`web/src/apis/domain_factory_api.js` 的 `withDemoFallback` 让 seed/extract/confirm/regex/提示词保存等在 demo 模式下返回 `{success:true, demo:true}`（`:284-342`、`:276-280`），契约错误被静默吞掉。

### X9 上传接口返回的 id 不是任务主键

`POST /domain-factory/upload` 返回的是落盘文件名里的 uuid，不是 `domain_factory_tasks.id`（§4.8.2）。当前前端只把它打日志，所以是潜在缺陷；但它是"上传即跳工作台"这类增强的硬阻塞，且错误信息表现为 `GET /tasks/{id}` 404，很难从页面看出来。

### X10 错误契约三套并存

同一个"用户操作失败"，前端可能收到：`HTTPException(400)`、`500` 包裹的 `ValueError`、`200 + {success:true, error:"..."}`、`404`（实际是内部错误）。三页的 `catch {}` 吞异常因此看不出差异（§4.8.3）。

### X11 服务"单例"名不副实，实例缓存形同虚设

`get_domain_factory_service()` 每次 new（§4.8.5），`_prompt_templates`、`_template_matcher` 的实例缓存每请求重建；`save_prompt_config` 声称的缓存失效只作用于当前实例。提示词配置"改了要等一会儿才生效"的观感与其无关（真因见 X2），但这个假缓存会让人误判。

#### 4.8.4 事务边界与幂等（与 X6 同源，后端侧证据）

- 每次 repo 调用退出即 commit（`manager.py:2375-2383`），单次 `POST /commit` ≈ **8+ 独立事务**。
- `confirm-region` 三步（update_task → confirm_facts → 逐条模板重算）无事务边界，失败留半完成态（`service:6654-6691`）。
