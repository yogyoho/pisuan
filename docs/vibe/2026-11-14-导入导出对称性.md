# 导入/导出对称性（2026-11-14）

依据：`docs/vibe/2026-11-14-领域实体构建器页面设计诊断.md` §4 P1-5。前两批解决的是「删除/改名前的引用影响面」，本批补上同一类问题的写入侧：导入是一把重锤，却既不告诉你要改什么，也在跨环境文件上直接 500。

## 目标

1. 跨环境导入（同一 `entity_key`、不同 `entity_id`）不再 500，而是按 `entity_key` 对齐成「更新」。
2. 没有 `entity_id` 的条目不再被静默跳过。
3. 导入前先算影响面：新增多少、更新多少、拒绝多少（含逐条原因），确认后才写库。
4. 归属其他行业域的条目（如旧文件里的 `coal`）被拒绝并说明原因，不再落成通用域里「看得见但用不上」的幽灵实体。

## 现状（问题）

- `upsert_all` 只按 `entity_id` 匹配（repo:156-196）：导出文件换环境后 `entity_id` 是本地代理键、对不上，于是走插入分支，撞 `entity_key` 唯一约束 → 500；条目缺 `entity_id` 时 `continue`，前端仍提示「导入成功，共 N 个实体」（N 只统计真正写入的，用户看不到跳过）。
- 导入只读 `entity_schemas`，`taxonomy` 被丢弃（不报错也不说明）。
- 无 preview / dry-run / 差异确认；导入即写，写错只能手工回滚。
- `domain_code` 不校验，且 repo 新建默认值是 legacy `"coal"`：旧文件导进来会得到 `domain_code=coal` 的行，而 ETL 与构建器都只读 `general`。

## 关键判断

- **对齐键选 `entity_key`，不是 `entity_id`。** `entity_key` 是引用契约（`entity_ref = entity_key.prop_key`）的实际标识，`entity_id` 只是环境内代理键。跨环境导入时保留本地 `entity_id`，避免主键漂移。
- **`taxonomy` 不导入。** 导出侧的 `taxonomy` 由实体的 `category` 现场派生（repo:241-260），它没有独立存储。导入了也不会被读，因此文档与弹窗里明确写「由分类派生，不参与导入」，而不是伪造成一种「已处理」。
- **行业域不符一律拒绝，不做自动改写。** 自动把 `coal` 改成 `general` 会让用户以为旧文件已完整迁移，实际业务语义可能不同；拒绝 + 原因让管理员先决定。
- **导入的属性变更要重映射待审核任务。** 单条保存走 `_remap_waiting_review_tasks`（service:230），批量导入如果不走，属性被覆盖后待审核任务的 `entity_ref` 会悬空。只要本批有更新，就复用同一函数。

## 范围

**做**

- `repo.upsert_all`：按 `entity_key` 匹配；新增行有 `entity_id` 就用、没有则生成 `uuid4`；返回写入条数。
- `service.import_all(config, dry_run=False)`：逐条校验（`entity_key` / `name_cn` / `domain_code`）、复用 `normalize_value_type` / `normalize_properties` 归一、统计 `created` / `updated` / `rejected[{index, entity_key, name_cn, reason}]`；`dry_run` 时只算不写；有更新则重映射待审核任务。
- `POST /import?dry_run=true|false`：返回结构化结果与中文 message。
- 前端导入弹窗：解析文件 → 先 `dry_run` 预检 → `Modal.confirm` 展示新增/更新/拒绝条数与拒绝原因（最多 5 条）→ 确认后真正导入 → 用后端 message 提示并刷新。
- 弹窗与文档说明 `taxonomy` 由分类派生、不参与导入。

**不做**

- 备份 / 撤销 / 版本历史（需要独立的快照机制，单列一批）。
- 导入时按 `entity_key` 做属性级三方 diff 预览。
- `domain_code` 作为导入参数开放（构建器只服务通用域，参数会制造第二条幽灵路径）。

### 顺带修掉的数据缺陷

回导预检暴露一类存量脏数据：**8 个实体**的属性把模板 slot 类型 `parameter` 写进了
`value_type`（共 44 条属性）。这类值既不是合法值类型也不是历史别名，导致这些实体在页面上
任何一次保存都会 400，导出文件也无法回导。新增治理脚本
`backend/scripts/governance/normalize_property_value_types.py`（幂等，默认 dry-run）：
`parameter` 按 key 判定归一——以「数值」结尾 → `Float`，其余 → `String`；历史别名交给写入
路径的 `normalize_value_type`，未知类型直接报错交人工确认。本机已 `--apply`（8 个实体），
库内非法值类型清零，回导不再拒绝。

```bash
docker exec pisuan-localized-api-1 python -u -m scripts.governance.normalize_property_value_types            # 预览
docker exec pisuan-localized-api-1 python -u -m scripts.governance.normalize_property_value_types --apply    # 写库
```


## 验收

1. 导出一份当前配置 → 原样导入：`created=0`、`updated=71`、`rejected=0`，无 500。
2. 把导出文件里某实体的 `entity_id` 改成任意值再导入 → 该实体计入 `updated`，库里 `entity_id` 不变（仍为原值）。
3. 构造一个只有 `entity_key`/`name_cn`、没有 `entity_id` 的条目 → 计入 `created` 并出现在实体树上（不再静默跳过）。
4. 构造 `domain_code: "coal"` 的条目 → 计入 `rejected`，原因写明归属行业域不符，库里不出现该行。
5. `dry_run=true` → 返回同样的计数，库里无任何变化。
6. 前端：选文件确定 → 先出现影响面确认弹窗（条数 + 拒绝原因），取消后库不变；确认后提示「新增 X，更新 Y」，实体树刷新。
7. 无 JS 报错；后端单测/集成测试通过。
